# API architecture (Python, FastAPI)

Decide how a Python API is structured and hand back a concrete layout. The default is a modular
monolith: one package per domain, layers inside, and more structure added to one module at a time
when a pain shows. The reasoning is in the guide; the rules below are what the code must follow.

Read the guide before recommending anything:
[references/guides/architecture--python--guides--api-structure.md](./references/guides/architecture--python--guides--api-structure.md)
holds the two layouts (domain modules and hexagonal modules), their costs and the signals to move a module to hexagonal.

## Workflow

1. **Look at what exists.** For a path, list the packages and read `main.py`, one router and one
   service. Note the framework, the ORM, how tests reach the database and the endpoint count. For a
   description only, ask for the domain's main areas and whether the rules are mostly CRUD.
2. **Place it.** Name the current layout and the pain, if any, using the signals in the guide's
   Evolution section. No pain means no move.
3. **Recommend one step.** Pick the smallest change that removes the pain: a domain split, a service
   extracted from a router, hexagonal layers in one module. Say what you would not do yet, and why.
4. **Show the layout.** Give the tree for the chosen layout and where the next three pieces of code
   would go. State the import direction: routers know services, services know the domain, adapters
   know the domain, never the reverse.
5. **Hand off.** Writing the code is the `python-developer` agent's job; give it the layout and the
   module to start with. Do not edit the project yourself unless asked.
